# 03. Incident report: session #12, 2026-10-31

**Status:** open (root cause probable, not confirmed) · **Severity:** high: recording ended about 55 minutes into a live session · **Format:** blameless

## Summary

During session #12 ("Role Playing" voice channel, 5 speakers), two independent problems occurred:

1. **Transcription fell far behind.** The worker converted about 4–5 clips per minute while about 27.5 arrived. By the end, more than 1,200 clips were queued, about 4.5 hours of work.
2. **The bot process exited mid-recording at about 21:36 local (02:36 UTC).** Recording stopped. The worker and the optional monitor kept running. On its next start the bot will mark session #12 `failed` ("Interrupted while recording").

No audio already recorded is lost. The WAVs not yet transcribed are still on disk and `/scrib process` will finish them. Speech after 21:36 was not recorded.

## Analysis

### Why the bot exited (probable)

No log file exists, and no Windows Application event was recorded. That is consistent with a JavaScript-level exit (an uncaught exception or unhandled rejection exits with code 1), not a native crash. It is equally consistent with the console window being closed or Ctrl+C, though Ctrl+C would have printed `[scribbot] shutting down` to a console that no longer exists.

The leftover **`timeline.json.tmp`**, stamped the same second as the last good `timeline.json`, is the strongest clue. The recorder writes the temp file and then renames it over `timeline.json` (`bot/src/recorder.ts:181-183`), about every 2 seconds during play. A `.tmp` that was never renamed means the process stopped between those two calls, or the rename threw. A rename that throws there becomes an **unhandled promise rejection**, which ends Node 24 by default ([02 S1](02-stability.md#s1-critical-clip-finalization-can-reject-unhandled)). On Windows, that rename fails with `EPERM`/`EBUSY` whenever another process (typically real-time antivirus scanning, or the search indexer) has the freshly written file open.

The alternative is a voice or gateway `error` event with no listener ([02 S2](02-stability.md#s2-critical-no-error-listeners-on-the-discord-client-or-voice-connection)). That would not explain the leftover `.tmp`, but it can't be ruled out without logs.

**Ruled out:** the new monitor panel (S11) wasn't running. The monitor process alive at the time was started at 20:34 with the previous code, which doesn't read session files while the bot is online. The assessment's own read-only analysis scripts ran after 21:38.

### Why transcription fell behind

See [01-performance-and-cpu-offload.md](01-performance-and-cpu-offload.md). In short: sub-second clips each cost a full 30-second Whisper window; about 130 Foundry monster names sent as hotwords on every clip made Whisper hallucinate them ("dragon" ×73) and retry; and 54% of clips yielded nothing usable but were fully processed. The GPU was 63% utilized and the CPU about 10%.

### Contributing factors

- No supervisor: nothing restarted the bot ([02 S3](02-stability.md#s3-high-a-bot-exit-ends-the-recording-for-good)).
- No persistent logs: the cause can't be confirmed ([02 S9](02-stability.md#s9-medium-no-persistent-logs)).
- No alert for a growing backlog: the 1,000+ clip queue was visible only on the dashboard ([02 S5](02-stability.md#s5-high-worker-queue-is-in-memory-and-unbounded)).

## Recovery steps (for the operator)

> **Status:** session #12 is recovered. The restarted worker converted all 1,513 clips from disk, and `transcript.json` and `transcript.md` were written at 23:10. It has no summary yet because `LLM_MODEL` is empty (05 C9).

1. Leave the worker running until its queue drains, or at least until session #12's clips are done. Stopping it now drops the queue (the WAVs remain, so it's recoverable, just slower).
2. Start the bot (`.\start.ps1`; it detects that the worker is already running).
3. Run `/scrib process` for session #12. It reuses the clips already converted (`transcript.partial.jsonl`) and transcribes the rest.
4. Optionally clean up the leftover `data\sessions\2026-11-01-6ae0bcc6\timeline.json.tmp`. It's harmless; the next timeline write overwrites it.
